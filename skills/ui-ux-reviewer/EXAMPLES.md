# UI/UX Reviewer examples

These are illustrative inputs and expected procedures, not fabricated audit results or claims that a project was tested. Populate evidence only after inspecting the real project.

## Example 1 — Signup flow review

### Input

> Review our signup flow and tell me what to improve first.

### Expected behavior

1. Identify target users and complete the available signup states using a test account if authorized.
2. Inspect labels, validation, password/recovery guidance and confirmation state.
3. Rank blockers with evidence and exact suggested changes.

### Expected output structure

Task/scope → journey observations → prioritized issues → acceptance checks → untested states.

### Boundary

Do not invent conversion rates or claim that a proposed change will increase signups by a percentage.

## Example 2 — Screenshot-only critique

### Input

> Here is a dashboard screenshot. Review its usability.

### Expected behavior

1. Identify visible hierarchy, labels and competing actions.
2. Ask for the primary task only if it materially affects the review.
3. Label keyboard, responsive and interaction behavior as unknown.

### Expected output structure

Visible observations → likely friction labeled as hypotheses → concrete visual changes → interaction checks still needed.

### Boundary

Do not report working or broken controls from a static screenshot.
